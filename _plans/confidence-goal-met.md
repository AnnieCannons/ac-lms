# Goal-Met Celebration, "What Helped" & Reminder (confidence-tracker-v2, Phase 6)

## Context
Phases 2–5 capture ratings/goals, show trend pages, and show a small kudos when a rating rises. Nothing yet notices when a student *reaches* the goal they set, asks what got them there, or lets them set a next goal. Phase 6 (spec: [`_specs/confidence-goal-met.md`](../_specs/confidence-goal-met.md), branch `claude/feature/confidence-goal-met`) adds: a goal-met celebration + optional multi-select "what helped" (met goals only), a mastery celebration (no question), a follow-up on My Skill Confidence, a reminder in the bell right away (bell only; stays until answered or cleared), and a student-only "Set a goal" control (after a met goal, or for a skill that never had one). Everything stays behind `CONFIDENCE_TRACKER_V2_RATINGS_ENABLED`, which stays **off** in production until all phases are done and the user is asked first.

## Findings that shape the design
- **Pre-existing bug Phase 6 makes unavoidable.** `skill_progress` has `CHECK (target_date > CURRENT_DATE)`, and `saveConfidenceRatings` re-sends the stored `target_date` on every upsert (`confidence-tracker-actions.ts:~177`). Once a goal's date passes, *any* later rating of that skill fails the progress upsert (after the rating row was already inserted, and the dedupe guard blocks a retry). A goal met after its target date — explicitly supported by the spec — would hit this every time. The migration drops that CHECK (future-date is still enforced in app code by `validateGoalInput`, and `goal_history` already has no such CHECK).
- `goal_history` is written only by a trigger on `skill_progress` (snapshots whenever goal/date/plan change), has no write policies, and has no per-goal "met" concept. The current goal is the newest history row after the latest `reactivated` event; reactivation clears the goal on the progress row.
- `notifications.type` has no CHECK (no migration for a new type); inserts need the service client; there is no dedupe; the digest email uses an allow-list (`grade_posted`, `submission_comment`) so a new type is automatically bell-only; `NotificationBell` derives its link from type/`course_id`/`assignment_id` (needs a new branch).
- (Superseded during implementation: the reminder is no longer a scheduled job, so the cron and student-timezone findings no longer apply. See the revised Reminder decision below.)
- `STUDY_PLAN_OPTIONS` has **no max length** on "Other" text today (only non-blank).

## Design decisions
- **New table `confidence_tracker_goal_outcomes`** (one row per *met* goal, `UNIQUE (goal_history_id)`) instead of columns on `goal_history`: keeps `goal_history` append-only, and the unique key gives "a goal is met at most once" and "older goals get no catch-up" for free. Holds met facts, the answer, and reminder state. Columns: `goal_history_id` (FK, cascade), `student_id`, `skill_id`, `met_at`, `met_rating`, `met_assignment_id` (nullable, SET NULL), `student_timezone` (nullable), `what_helped text[]`, `what_helped_other`, `answered_at`, `reminder_sent_at`, `reminder_notification_id`. CHECKs: allowed values subset, `'other'` ↔ non-blank `what_helped_other`, `answered_at` set iff answers non-empty, other-text length cap. RLS: SELECT own or admin/instructor/staff (TAs excluded); **no write policies** — writes go through server actions using the service client *after* explicit auth/role checks (CLAUDE.md pattern), so add-only is enforced in code (`UPDATE … WHERE answered_at IS NULL`).
- **Goal met is decided at save time inside `saveConfidenceRatings`** (like kudos), using the pre-upsert `progressBySkill`: numeric goal present, `rating >= goal`, head `goal_history` row for the skill has no outcome. Maintaining goals never match. Mastered skills are already gated out. Outcome insert uses `ON CONFLICT DO NOTHING` (idempotent). If the outcome insert fails, skip the celebration rather than failing the save (the goal stays open, so a later qualifying rating celebrates).
- **Mastery celebration** comes from `nextMasteryState(...).justMastered` (hoisted out of the upsert map). No outcome row, no question, nothing stored. If the same rating also meets a numeric goal of 10, one combined celebration; the question is asked once, for the goal; no next-goal step.
- **Return shape** widens to `{ error, kudos, celebrations }`; the server removes celebrated skills from `kudos` (celebration replaces kudos). Flag off → no outcomes created and nothing returned (ratings still save). `celebrations[]` items: `{ skillId, rating, mastered, goal?: { outcomeId, target, ownPlanText? , nextGoalAllowed } }`.
- **"What helped" options** live in `confidence-tracker-validation.ts` beside `STUDY_PLAN_OPTIONS`, reusing the same six values (so Phase 7 can join "planned" with "helped") with past-tense labels, plus `other`, plus `own_plan` (the student's own study-plan "Other" text for that goal, valid only if that goal's history row has one; displayed from the history row). "Other" text cap: add one shared `OTHER_TEXT_MAX_LENGTH` (200) applied to both study-plan and what-helped "Other" (spec says "same as study plan"; none exists today).
- **Next goal** = guarded `UPDATE` of the student's `skill_progress` row (the existing trigger then writes the `goal_history` snapshot — never insert history by hand). Allowed when not mastered and (no goal, or current goal has an outcome). Uses the latest rating and `validateGoalInput`. Double-click safe via an optimistic check on the row's `updated_at`. Latest rating 10 → UI shows the "maintaining this rating" note, no control, nothing written.
- **Reminder (revised after review; answering changed 2026-10-05 to also clear it)**: no scheduled job. When a goal is reached, `saveConfidenceRatings` creates the bell notification immediately (`type: 'confidence_goal_what_helped'`, message "You reached your goal of N in [skill]. Log what helped.", no course/assignment ids so the bell doesn't link to an assignment, `emailed_at` left null so the digest allow-list never emails it) and links it via `outcome.reminder_notification_id`. Answering (`answerWhatHelped`) only marks it read; it stays until the student clicks it (which opens My Skill Confidence and clears it) or uses **Clear**. The student can **Clear** any notification in the bell: a new nullable `notifications.cleared_at` hides the row from the bell without deleting it (so the digest email is unaffected); clearing never touches the follow-up on My Skill Confidence. Creation is best-effort and separate from recording the outcome, so a failed notification never drops the celebration.

## Changes

### 1. Migration — `supabase/migrations/20260930000000_confidence_tracker_goal_outcomes.sql` (idempotent, hand-applied)
- Create the outcomes table (+ indexes on `(student_id, skill_id)`), RLS SELECT policy, `GRANT ALL … TO anon, authenticated, service_role`, per the repo's table shape.
- Second migration `20260930010000_notifications_cleared_and_reminder_simplify.sql`: adds `notifications.cleared_at`, and drops the now-unused `reminder_sent_at` and `student_timezone` columns and the pending-reminder index from the outcomes table.
- `DO` block that finds and drops the `target_date > CURRENT_DATE` CHECK on `confidence_tracker_skill_progress` by definition (name is auto-generated), guarded so it is safe to re-run.
- Update `SCHEMA.md` (new table + index rows; fix the stale "goal only set with a new rating" note).

### 2. Pure logic (Supabase-free, unit-testable)
- New `src/lib/confidence-celebrations.ts`: `computeCelebrations(entries, progressBySkill, headGoalBySkill, masteryBySkill)` → items (met goal / mastered / both); helper to drop celebrated skill ids from kudos.
- `src/lib/confidence-tracker-validation.ts`: `WHAT_HELPED_OPTIONS`, `validateWhatHelped(input, ownPlanText)`, `OTHER_TEXT_MAX_LENGTH` (applied in `validateGoalInput` too).
- `src/lib/confidence-trend.ts`: `GoalRow`/`TrendGoal` gain `id` and an optional `met` ({ metAt, rating, outcomeId, answer }); `SkillTrend` gains goal status (none / open / met / maintain) and `canSetGoal`; current-goal logic treats a met goal as current-but-closed.

### 3. Server actions
- `src/lib/confidence-tracker-actions.ts` (`saveConfidenceRatings`): after the progress upsert succeeds — read head `goal_history` row per candidate, insert outcomes and their bell reminders (service client), compute celebrations, strip celebrated skills from kudos, return `celebrations`. Existing early returns unchanged. Hoist `justMastered`.
- New `src/lib/goal-met-actions.ts` (`'use server'`, pattern copied from `reactivateConfidenceSkill`: flag → input → auth → reject admin/instructor/staff → operate on own rows only; non-blaming errors; `{ error }` results):
  - `answerWhatHelped(outcomeId, selections, otherText)` — add-only, duplicate is a harmless no-op; marks the reminder read (it stays in the bell until clicked or cleared).
  - `setSkillGoal(skillId, goalInput)` — rules above.
- Observers: they have no ratings/progress rows of their own, so both actions are naturally no-ops for them (same reasoning as reactivate); covered by the row-ownership checks.

### 4. Reminder in the bell (no cron)
Created inside `recordCelebrations` (see the Reminder decision above); message and type live in `src/lib/goal-met-notification.ts`. `notification-actions.ts`: `getMyNotifications`, `getInstructorNotifications` and `getInstructorUnreadCount` skip cleared rows; new `clearNotification(id)`.
- `src/components/ui/NotificationBell.tsx` `notificationHref`: new first branch for the new type → `/student/skill-confidence#what-helped`. Each item also gets a **Clear** button (separate from the clickable message) that hides just that notification; clicking the "what helped" reminder itself opens My Skill Confidence and clears it.

### 5. UI
- **Shared `GoalFields.tsx`** extracted from `ConfidenceRatingPrompt.tsx` (goal scale buttons, `DatePickerField`, study-plan checkboxes, "Other" input, `suggestedGoal`, `defaultTargetDate`). `ConfidenceRatingPrompt` renders it, behaviour unchanged. Reused by the next-goal step and My Skill Confidence.
- **Shared `WhatHelpedForm.tsx`**: checkbox group over `WHAT_HELPED_OPTIONS` (+ own-plan option) with "Other" input, Save / Skip.
- **`GoalMetCelebration.tsx`** (beside `ConfidenceKudos`, same `kudos-card`-style class + new `.celebration-card` in `globals.css` using the theme-aware teal `color-mix` vars): one card for all celebrated skills, `role="status"` heading, each met goal shows its question, then an optional next-goal step (not for mastery or rating 10). Skip = dismiss = walking away. Text-based, reduced-motion safe (global rule).
- `SubmissionForm.tsx` (`handleSubmit`, ~L303): keep `celebrations` state next to `kudos`; map ids to names via `confidenceSkills`; render above the view-mode block. Failure keeps the existing `ratingError` banner and shows neither.
- **My Skill Confidence**: `confidence-trend-data.ts` loads outcomes in `loadStudentTrend` and `loadCourseTrend`; `SkillTrendCard.tsx` shows a neutral "Goal met on <date>" and the answer (or "Not answered yet") in `GoalPanel`/`GoalLine` (this is also what the instructor per-student view shows, read-only — no new instructor code path); `SkillConfidenceView.tsx` adds a top "What helped?" summary (`id="what-helped"`, shown only when unanswered items exist), a per-skill footer item opening the form in the existing `Modal`, and a "Set a goal" button (Modal + `GoalFields`) when `canSetGoal`; both disabled/hidden for staff via the existing `canReactivate`-style prop. `router.refresh()` after success, as reactivate does.
